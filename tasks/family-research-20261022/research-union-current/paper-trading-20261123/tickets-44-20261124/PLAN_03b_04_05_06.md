## Ticket 04: nothing keeps the outcome from the challenger until the challenge is on record

- One door in `tools/kgraph/defend.py`: `defend outcome --claim <id> --run run:NNNN --record <repo>:<path>@<commit>
  [--record ...] --out <folder>`. It is the only code that hands a claim's outcome-bearing records (a trial's
  kept files, an afterwards file) to an agent run.
  - The claim is a registered claim; the run is an AgentRun.
  - A run whose role is the reviewer's: refused unless THAT run's own independent challenge of the claim's
    current revision is on record.
  - Any other run: refused unless at least one independent challenge of the current revision is on record.
  - A refusal is retained as a Task node, like every other refusal of defend.
  - A release copies each record to `--out` (each file's sha256 checked against the bytes at its commit) and
    writes one Task node, state `done`: the claim, its revision, the run, each record's repo, path, commit,
    sha256 and bytes, the challenges on record at that moment, the time. A MENTIONS link ties it to the claim.
    `defend show` lists a claim's releases: who was handed the outcome, when.
- The brief of a claim never names an outcome record: registration refuses a claim whose artifact or ground is
  a file the claim file lists under a new optional key `outcome_records` (the files that will bear this
  claim's outcome), and the brief does not print that key.
- Checks: before the reviewer run's challenge the door refuses it and the refusal is on record; after the
  challenge is on record the same call releases, and the release is on record with the files' hashes; a
  second reviewer run with no challenge of its own is still refused; the brief of that claim holds none of the
  record paths.
- WHAT THIS DOES NOT COVER, said in the docstring and in the ticket: code cannot see an agent that opens a file
  it was not handed; and the loop's own hand-over (`tools/ratchet/file_proposer.py` `kept_records`, which
  points the next proposer at earlier trials' folders, and `tools/decider/afterwards.py brief`, "for writing
  the next decider") is not put behind the door here, because a trial of the loop is not yet tied to a
  registered claim. That tie is ticket 01's second half and ticket 39; until then the proposer's sight of the
  earlier outcome is what its claim's `outcome_visibility` must say.

## Ticket 05: a check is written after a trial

- `defend check --claim <id> --file <check.json> --run run:NNNN`. The check file:
  `inputs`: a list of `{"what","repo","path","commit"}`, each resolved and hashed by code (one shape with the
  data hashes of the fix round); `checks`: one entry for EACH falsifier of the claim's current revision, by
  its number: `falsifier`, `check_type` (deterministic or model-assisted), `method`, `method_version`,
  `location`, `scope`, `what_was_checked`, `what_was_observed`, `what_remains_open`, `reproducibility`,
  `exceptions`, and `falsifier_observation_seen`: yes, no or not determined.
- Refused: a falsifier of the current revision with no entry (named); an entry for a falsifier that is not
  registered; a run that registered any revision of the claim (the proposer does not write its own check); a
  claim with no independent challenge of its current revision on record (the order is register, challenge,
  trial, check); a verdict label.
- Written, one Evaluation node for each falsifier: rubric `falsifier check v1: ...`; the three plain fields;
  the contract fields of `schema.EVALUATION_CONTRACT_FIELDS` with `expected_observation` COPIED BY CODE from
  the registered falsifier, `claim_revision` by code, `input_hash` the hashes code computed, `reviewer` the
  run. EVALUATES to the claim, PRODUCED from the run. No verdict field.
- `defend unchecked` lists each registered claim's falsifiers that have no check on record; `defend show`
  lists the checks.
- Built and checked without the engine: the checks use a scratch copy of the real graph and real files of
  markets-data as inputs. Shown on a real trial only at the first pass on tape, which is Greg's go (ticket 40).

## Ticket 06: adverse evidence is on record

- When a check entry says `falsifier_observation_seen: yes` it must carry `observed_at`: the input it was seen
  in, the lines and the quoted words. Code then writes, in the same write as the Evaluation: a counter Claim
  (the pattern of `tools/swarm/refute.py`: text the entry's `what_was_observed`, statement kind measurement,
  not an inference, its source the input file with those lines and quote, `counter_to` the claim) and a
  CONTRADICTS link from the counter claim to the registered claim, carrying the check's id and the falsifier's
  number. Both claims stand; nothing is withdrawn or marked as replaced.
- The session text: `tools/kgraph/context.py` gains a section OPEN CONFLICTS, built from the live CONTRADICTS
  links and not from a statement kind: each link its own line (the claim, the counter claim, the first words of
  each, the check), shown ahead of the budgeted sections and counted in the budget; with no link the section
  says none is on record. A link taken back (`resolve undo`, with its reason) leaves the section. This is also
  what ticket 26 asks; it is built once, here.
- Checks: after a check with a seen falsifier, the graph holds the counter claim and one live CONTRADICTS link,
  the registered claim is still there at the same revision, `grounding claim` lists the conflict as open, and
  the session text's OPEN CONFLICTS section shows the pair; after the link is taken back the section no longer
  shows it and both claims are still there.
- GREG'S TO SETTLE (asked 2026-11-24, not answered): whether a revision also writes a REVISES link and whether
  a reviewer's objection in a challenge also writes a CONTRADICTS link. Built meanwhile: neither; an objection
  stays on the challenge's own record. If he says yes to either, it is added, nothing is undone.

1. NOT GREG'S TO SETTLE AGAIN: THE ZIP SETTLES IT. The adoption plan's 4a-bis: "a claim revision is a REVISES

   - A revision of a registered claim writes a REVISES link from the later wording to the earlier one. The
     store refuses a link from a thing to itself (`schema.check_edge`), and today every revision is a store

     earlier wording is also written as a Claim node `<claim id>#r<N-1>` holding that revision's fields as
     they were, with `revision_of: <claim id>` and marked so that it is never listed as a second live claim
     (the session text, `undefended` and `unchecked` list the stable id only). REVISES runs from `<claim id>`
     to `<claim id>#r<N-1>`, and from each `#r<K>` to `#r<K-1>`. Nothing is withdrawn to make this so. THE
     REVIEWER IS ASKED to say whether this keeps "every superseded object stays addressable" and whether a

   - A refutation writes a CONTRADICTS link. Two things are a refutation: a check after a trial in which the
     falsifier's observation was seen (as planned under ticket 06), and an objection in an independent
     challenge that states evidence against the claim with its source (file, lines, quoted words); an
